# RAG Server (FastAPI + Qdrant + Ollama)

A self-contained Retrieval-Augmented Generation (RAG) stack: upload documents, they get
chunked and embedded into Qdrant, and questions get answered by a local Ollama model
grounded in the retrieved chunks. Ships as three Docker Compose services plus a web
chat UI and a terminal test client.

## Architecture

```
 ┌─────────────┐      ┌─────────────┐      ┌─────────────┐
 │   rag-api   │─────▶│   qdrant    │      │   ollama    │
 │  (FastAPI)  │      │ (vector db) │      │ (local LLM) │
 │  + chat UI  │─────────────────────────▶│             │
 └─────────────┘      └─────────────┘      └─────────────┘
       ▲ :8000               :6333               :11434
       │
   your browser / chat_cli.py / curl
```

- **rag-api**: FastAPI app — chunking, embeddings, ingestion, retrieval, the web chat UI, and answer generation.
- **qdrant**: vector storage for embedded chunks.
- **ollama**: runs the local LLM used to generate answers; auto-pulls your chosen model on first boot.

## Features

- Ingest raw text, a local file path, an uploaded PDF (`POST /ingest/pdf`), or a whole
  directory of `.pdf` / `.txt` / `.docx` / `.xls` files (`ingest_dataset.py`)
- Embeddings via a local `sentence-transformers` model (`EMBEDDING_MODE=local`, default,
  fully offline) or an external embedding API (`EMBEDDING_MODE=api`)
- Answers generated by a local Ollama model, with an automatic extractive fallback if
  Ollama is unavailable or `use_llm: false` is passed
- Minimal web chat UI at `/` — ask questions, toggle LLM vs. extractive, upload PDFs
- Auto-ingests everything under `dataset/` on first boot, resilient to a slow/flaky
  Qdrant startup (retries + a connectivity heartbeat)
- `chat_cli.py` — a terminal client that talks to the pipeline directly, useful for
  seeing real Python tracebacks instead of a generic browser error

## Quick Start (local Docker Compose)

```bash
cp .env.example .env
# edit .env: pick OLLAMA_MODEL (e.g. llama3.2, mistral, qwen2.5), embedding mode, etc.

docker compose up --build
```

Open **http://localhost:8000** for the chat UI.

- The `ollama` service pulls `OLLAMA_MODEL` on first startup (see `ollama/entrypoint.sh`) — can take a while for larger models.
- Data persists in the `qdrant_data`, `ollama_data`, and `hf_cache` named volumes across restarts.
- To switch models later: change `OLLAMA_MODEL` in `.env`, then `docker compose up -d ollama`.

## Deploying to a Remote Server

### 1. Package a clean copy

`package.sh` copies the project into a sibling folder, stripping `.venv`, caches, `.git`,
and anything not needed to run (see the script for the exclude list):

```bash
./package.sh
# -> writes to ../RAG_Server_deploy
```

Re-run it any time after making changes — it's the folder you actually ship.

### 2. Copy it to the server

```bash
rsync -avz --progress ../RAG_Server_deploy/ your-host:~/RAG_Server_deploy/
```

### 3. Run it there

```bash
ssh your-host
cd ~/RAG_Server_deploy
cp .env.example .env   # edit as needed
docker compose up --build -d
```

If `docker` needs `sudo` on that box (permission denied on `/var/run/docker.sock`), either
add your user to the `docker` group (`sudo usermod -aG docker $USER`, then reconnect) or
just prefix every command with `sudo`.

### 4. Access it via SSH tunnel

Don't expose the port publicly on a shared server — tunnel it instead:

```bash
ssh -L 8000:localhost:8000 your-host
```

Then open **http://localhost:8000** locally. To make this automatic, add a
`LocalForward 8000 localhost:8000` line to that host's entry in `~/.ssh/config`.

If you changed `RAG_API_HOST_PORT` (see below), tunnel that port instead.

### Redeploying after a code change

Only `rag-api` needs to be touched for an app-code change — no need for `docker compose down`:

```bash
./package.sh
rsync -avz --progress ../RAG_Server_deploy/ your-host:~/RAG_Server_deploy/
ssh your-host 'cd ~/RAG_Server_deploy && docker compose up --build -d'
```

Compose only rebuilds/recreates what actually changed.

## Configuration (`.env`)

See `.env.example` for the full list with defaults. Key ones:

| Variable | Default | Purpose |
|---|---|---|
| `OLLAMA_MODEL` | `llama3.2` | Model auto-pulled on Ollama startup and used for answers |
| `EMBEDDING_MODE` | `local` | `local` (sentence-transformers, offline) or `api` (external embedding endpoint) |
| `EMBEDDING_MODEL` | `sentence-transformers/all-MiniLM-L6-v2` | Model used when `EMBEDDING_MODE=local` |
| `QDRANT_COLLECTION` | `Beees` | Qdrant collection name |
| `AUTO_INGEST_ENABLED` | `true` | Auto-ingest everything under `AUTO_INGEST_DIR` on first boot |
| `AUTO_INGEST_DIR` | `dataset` | Directory scanned for `.pdf`/`.txt`/`.docx`/`.xls` on first boot |
| `QDRANT_HEARTBEAT_ENABLED` | `true` | Background thread pinging Qdrant, logs only on reachability changes |
| `RAG_API_HOST_PORT` / `QDRANT_HOST_PORT` / `OLLAMA_HOST_PORT` | `8000` / `6333` / `11434` | Override if a port's already taken on a shared server |

## Data Ingestion

**Automatic**: on first boot (empty Qdrant collection), `rag-api` extracts and embeds
every `.pdf`, `.txt`, `.docx`, and `.xls` file under `AUTO_INGEST_DIR` (default `dataset/`,
which ships with the bee dataset) in the background. Runs once — later restarts skip it
once the collection has data. Watch it:

```bash
docker compose logs -f rag-api | grep auto-ingest
```

**Manually re-ingest a directory** (e.g. after adding new files, or the collection
already had data so auto-ingest skipped):

```bash
docker compose exec rag-api python ingest_dataset.py --dir dataset
```

**Upload a single PDF** via the chat UI's upload button, or:

```bash
curl -X POST http://localhost:8000/ingest/pdf -F "file=@your-file.pdf"
```

**Ingest raw text** directly:

```bash
curl -X POST http://localhost:8000/ingest/text \
  -H "Content-Type: application/json" \
  -d '{"text": "RAG combines retrieval with generation.", "source": "intro"}'
```

## Terminal Test Client

For quick testing without the browser — and to see full Python tracebacks instead of a
generic "Internal Server Error" — use `chat_cli.py`. It talks to the pipeline directly,
in-process:

```bash
docker compose exec rag-api python chat_cli.py
```

Type a question, `/llm` to toggle LLM vs. extractive answers, `exit` to quit.

## API Reference

| Endpoint | Purpose |
|---|---|
| `GET /` | Web chat UI |
| `GET /health` | Health check |
| `POST /ingest/text` | Ingest raw text (`text`, `source`) |
| `POST /ingest/file` | Ingest a UTF-8 text file by path on the server |
| `POST /ingest/pdf` | Multipart PDF upload, extracted and ingested directly |
| `POST /ask` | `{question, top_k, use_llm}` → `{answer, contexts, mode}` |
| `POST /debug/embed` | Embed a list of texts directly, for verifying embedding config |

### `POST /ask`

```bash
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "How do bees communicate food location?", "top_k": 4, "use_llm": true}'
```

`use_llm: true` (default) sends retrieved chunks to Ollama and returns a generated
answer (`mode: "llm"`). If Ollama is unreachable or `use_llm: false`, it falls back to
an extractive answer built directly from the top chunks (`mode: "extractive"`).

## Troubleshooting

**`port is already allocated`**: something else on the host already has that port. Set
`RAG_API_HOST_PORT` / `QDRANT_HOST_PORT` / `OLLAMA_HOST_PORT` in `.env` to something free
(check with `sudo ss -tulpn | grep <port>`), then `docker compose up --build -d` again.
Internal container-to-container traffic (`rag-api` → `qdrant:6333`) is unaffected by
these — they only change the host-side mapping.

**`permission denied ... docker.sock`**: your user isn't in the `docker` group yet.
`sudo usermod -aG docker $USER`, then reconnect (`exit` and `ssh` back in) — `newgrp docker`
only affects the current shell.

**Intermittent `Connection refused` to Qdrant, especially on shared/cluster
infrastructure**: every Qdrant call already retries with exponential backoff
(`_qdrant_retry` in `rag_pipeline.py`), and a background heartbeat
(`QDRANT_HEARTBEAT_ENABLED`) logs exactly when reachability changes — check
`docker compose logs -f rag-api | grep heartbeat` to see if it's a real, ongoing
network issue on the host versus a one-off blip.

**Checking what's actually inside a container**: `chat_cli.py` bypasses the HTTP layer
entirely and prints full tracebacks, which is far more useful for debugging than a
browser's generic "Internal Server Error".

## Manual Setup (without Docker)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Set the same environment variables Compose sets (see the table above and
`.env.example`), pointing `QDRANT_URL` / `OLLAMA_URL` at wherever those services
actually run — `http://127.0.0.1:PORT` if running locally, `http://qdrant:6333` /
`http://ollama:11434` only applies inside the Compose network.

```bash
uvicorn app:app --reload --host 0.0.0.0 --port 8000
```

If Qdrant isn't running yet:

```bash
docker run -p 6333:6333 qdrant/qdrant
```

### API embedding mode details

If `EMBEDDING_MODE=api`, `EMBEDDING_API_URL` and `EMBEDDING_API_KEY` are required. Auth
is a `Bearer` token: `Authorization: Bearer <EMBEDDING_API_KEY>`. Expected request
payload:

```json
{ "model": "bge-m3", "input": ["text1", "text2"] }
```

Expected response — either a bare array of vectors, or an array of `{"embedding": [...]}`
objects.
